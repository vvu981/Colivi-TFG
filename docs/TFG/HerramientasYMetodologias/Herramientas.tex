\section{Herramientas usadas}
\label{sec:herramientas_usadas}

    Cada herramienta del proyecto responde a una exigencia técnica concreta de la arquitectura distribuida. Se descartaron soluciones monolíticas pesadas en favor de tecnologías con tipado estricto, bajo consumo de memoria y separación limpia entre dominios.

\subsection{Entornos de desarrollo y asistencia técnica}
\label{subsec:entornos_desarrollo}

    Antigravity actuó como entorno principal para programar el backend en Spring Boot y el microservicio en Node.js (figura~\ref{fig:entornos_desarrollo}). Su soporte para espacios de trabajo desacoplados facilitó mantener abiertos los servicios del servidor mientras se levantaban contenedores y terminales de depuración simultáneas. Frente a alternativas lentas como Eclipse, agilizó la navegación entre clases de dominio y la refactorización guiada.

    Visual Studio Code asumió el desarrollo del cliente web y el empaquetado móvil. El ecosistema de complementos para TypeScript, la integración con ESLint y el formateo automático con Prettier garantizaron coherencia estilística en todo el código de React. Alternativas como WebStorm ofrecían prestaciones equivalentes pero con una penalización innecesaria en el consumo de memoria RAM del equipo de desarrollo.

    Android Studio intervino en la fase final de empaquetado y prueba sobre dispositivos móviles. La lógica de la aplicación se comparte desde React gracias a Capacitor; sin embargo, compilar el paquete nativo APK (\emph{Android Package Kit}), firmar digitalmente el binario y depurar las llamadas al puente de WebView requirió la suite oficial de Android sobre emuladores del sistema operativo.

\subsection{Lenguajes, librerías y servicios}
\label{subsec:lenguajes_marcos_servicios}

    Java 21 y Spring Boot 3 forman el núcleo del servidor. Los registros inmutables (\emph{records}) y la concordancia de patrones (\emph{pattern matching}) de Java 21 aligeraron los objetos de transferencia DTO (\emph{Data Transfer Object}) eliminando código repetitivo. Spring Boot 3 resolvió la inyección de dependencias, las transacciones declarativas (@Transactional) y la seguridad sin estado con Spring Security mediante filtros para tókenes JWT (\emph{JSON Web Tokens}). Frente a soluciones basadas en Python o JavaScript, el tipado de Java evitó errores de redondeo en los cálculos contables. Spring AI facilitó además enlazar este backend con los modelos de lenguaje servidos por la API de Groq, forzando respuestas estructuradas en esquemas JSON.

    El microservicio del asistente inteligente se desarrolló con Node.js y TypeScript bajo el estándar \emph{Model Context Protocol} (MCP). Se aisló este módulo del backend central para que las herramientas de consulta operaran de forma independiente mediante \emph{Server-Sent Events} (SSE). TypeScript garantizó que los esquemas de entrada y salida de las funciones coincidieran exactamente con los tipos declarados por el cliente.

    React 18 estructura la interfaz web apoyándose en Vite como empaquetador. La compilación basada en módulos nativos (\emph{ES Modules}) de Vite redujo drásticamente el tiempo de refresco en caliente (\emph{Hot Module Replacement}). Tailwind CSS aceleró el diseño maquetando directamente en los componentes sin lidiar con hojas de estilo dispersas. TanStack Query centralizó la sincronización con el servidor: resuelve la caché, invalida consultas al mutar datos y refresca los saldos en segundo plano. Para la versión móvil se empleó Capacitor, envolviendo la base web en una vista nativa de Android sin reescribir la lógica en Kotlin.

\subsection{Almacenamiento y persistencia de datos}
\label{subsec:almacenamiento_persistencia}

    PostgreSQL 16 gestiona la persistencia de datos (figura~\ref{fig:postgresql_logo}). La naturaleza financiera de Colivi —balances de gastos, retención de fianzas y reservas de habitaciones— exige cumplir de forma estricta las garantías ACID (\emph{Atomicity, Consistency, Isolation, Durability}). Bases de datos no relacionales como MongoDB se descartaron por su incapacidad para garantizar transacciones multipartitas fiables sin configuraciones complejas. La comunicación entre las entidades Java y las tablas SQL se resolvió mediante JPA e Hibernate, optimizando las consultas mediante proyecciones DTO y fetch joins para atajar el problema de rendimiento por consultas $N+1$.

\subsection{Control de versiones, infraestructura y utilidades auxiliares}
\label{subsec:control_versiones_infraestructura}

    Git y GitHub gestionaron el versionado del código fuente mediante un flujo riguroso de ramas y solicitudes de extracción (\emph{pull requests}). Ningún cambio se incorporó a la rama principal sin revisión previa de pruebas unitarias.

    Docker y Docker Compose estandarizaron el entorno de ejecución. Se configuraron contenedores para levantar en local la base de datos PostgreSQL, el servidor Spring Boot y el microservicio MCP, replicando la misma infraestructura que se despliega en producción sobre Microsoft Azure.

    Figma (figura~\ref{subfig:figma}) sirvió para definir la tipografía, paleta de colores y maquetas previas de las pantallas para móvil y escritorio. PlantUML (figura~\ref{subfig:plantuml}) generó los diagramas UML directamente desde código de texto versionado en Git, mientras que draw.io facilitó la exportación de esquemas de bloques. Las pruebas manuales de endpoints REST y eventos SSE se ejecutaron con Postman (figura~\ref{subfig:postman}) y cURL antes de escribir los tests automatizados con JUnit 5 y Mockito.
