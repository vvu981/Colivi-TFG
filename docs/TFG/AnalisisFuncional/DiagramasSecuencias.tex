\section{Diagramas de secuencia del sistema}
\label{sec:diagramas_secuencia}

    Los diagramas de secuencia UML 2.5 detallan la dimensión temporal y el intercambio cronológico de mensajes entre componentes: el cliente en React, los controladores REST, los servicios de aplicación en Spring Boot, los publicadores de eventos de dominio, la base de datos PostgreSQL y los servicios externos conectados.

    La plataforma implementa ochenta y seis casos de uso, pero la mayoría realiza operaciones estándar de lectura o actualización. Se seleccionaron diez escenarios con lógica distribuida, salvaguardas de concurrencia o sincronización asíncrona:

\begin{enumerate}
\item Recuperación segura de contraseña con doble fase y mitigación de enumeración.
\item Alta de inmueble base con geocodificación cartográfica y compensación transaccional.
\item Solicitud de reserva con validación temporal de calendario y notificación multicanal.
\item Transición de estados y formalización del cobro de fianza en reserva aceptada.
\item Adhesión a un espacio de convivencia mediante código efímero y asignación de membresía.
\item Registro de gasto compartido con cálculo de matriz contable y simplificación de balances.
\item Baja o expulsión de un miembro con validación de saldo cero y rebalanceo de tareas.
\item Planificación periódica de tareas domésticas y resolución de rescate gamificado.
\item Interacción con el asistente inteligente mediante ticket efímero y protocolo MCP.
\item Tramitación y resolución de denuncias con auditoría de chat y suspensión cautelar.
\end{enumerate}

    La recuperación de credenciales opera en dos fases desacopladas (figura \ref{fig:seq_recuperacion_contrasena}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_recuperacion_contrasena.png}
    \caption{Diagrama de secuencia del proceso de recuperación segura de contraseña}
    \label{fig:seq_recuperacion_contrasena}
\end{figure}

    El usuario introduce su correo electrónico en el formulario web. El sistema aplica una política de defensa contra ataques de enumeración de cuentas (\emph{Anti User-Enumeration}): si la dirección no existe en la base de datos o la cuenta está suspendida, el servicio genera una traza interna y retorna un código HTTP 200 con cuerpo vacío. La interfaz muestra un mensaje estándar de confirmación. Ningún atacante puede inferir qué cuentas están dadas de alta. Si la cuenta existe, se genera un identificador UUID temporal con 24 horas de validez y se persiste en base de datos. ApplicationEventPublisher dispara de inmediato la notificación en segundo plano para que el servicio de correo despache el mensaje sin bloquear la respuesta HTTP al cliente.

    El restablecimiento concluye cuando el usuario abre el enlace con el token temporal e introduce la nueva contraseña. El backend comprueba la existencia del token y verifica que no haya vencido la marca de tiempo. Si la validación es correcta, la clave se procesa con el algoritmo de dispersión (\emph{hashing}) con sal criptográfica, se invalida el token temporal y se persiste la entidad, retornando un código 204 que redirige al usuario hacia el formulario de inicio de sesión.

    El alta de propiedades físicas combina geocodificación cartográfica con almacenamiento multimedia (figura \ref{fig:seq_alta_inmueble}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_alta_inmueble.png}
    \caption{Diagrama de secuencia del alta de inmueble con geocodificación y compensación transaccional}
    \label{fig:seq_alta_inmueble}
\end{figure}

    El proceso se divide en dos fases. El anfitrión introduce la dirección postal en el formulario del cliente web. La aplicación consulta el servicio de cartografía Nominatim (OpenStreetMap) para transformar el texto en coordenadas espaciales (latitud y longitud), posicionando el marcador en el mapa de Leaflet. Tras validar los campos estructurales (metros cuadrados, dormitorios y servicios), la petición viaja a POST /api/v1/accommodations. El controlador AccommodationController traslada la carga a AccommodationServiceImpl, donde la entidad se enlaza con el anfitrión mediante una referencia perezosa de JPA (userRepository.getReferenceById) y se persiste en PostgreSQL, retornando el identificador del alojamiento.

    La segunda fase gestiona la subida de las fotografías. La aplicación envía los archivos al servicio de almacenamiento en la nube y conserva la dirección pública de cada imagen en la base de datos. Si se produce un fallo de red o la base de datos rechaza el registro, el sistema elimina la fotografía que haya quedado huérfana. De este modo se mantiene sincronizada la información del inmueble con las imágenes asociadas.

    La solicitud de reserva gestiona restricciones de calendario y comunicación asíncrona entre las partes (figura \ref{fig:seq_solicitud_reserva}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_solicitud_reserva.png}
    \caption{Diagrama de secuencia de la solicitud de reserva con validación temporal y notificación multicanal}
    \label{fig:seq_solicitud_reserva}
\end{figure}

    El inquilino selecciona las fechas en el calendario interactivo y envía la petición mediante POST /api/v1/booking-requests. BookingRequestController recupera la identidad del solicitante desde el token JWT y traslada el objeto BookingRequestDto a BookingRequestServiceImpl. Antes de modificar datos, BookingRequestValidator ejecuta validaciones en cadena: comprueba que el usuario esté activo sin sanciones, que el anuncio permanezca publicado, que el solicitante no sea el dueño del inmueble, que no existan solicitudes duplicadas en trámite y que las fechas no colisionen con reservas confirmadas.

    Tras validar todas las reglas, el servicio instancia la entidad BookingRequest en estado PENDING y la persiste atómicamente en BookingRequestRepository. La transacción publica el evento de dominio BookingRequestCreatedEvent mediante ApplicationEventPublisher. Dos componentes escuchan este evento de forma desacoplada: BookingNotificationListener invoca a EmailService para redactar y enviar un correo transaccional al propietario, mientras BookingStatusChangedListener utiliza MessageService para registrar una notificación automática de sistema dentro de la conversación vinculada al anuncio. El controlador devuelve un código HTTP 201 con el DTO BookingRequestResponseDto confirmando el registro.

    La consolidación de la reserva se produce mediante la aprobación del anfitrión y el pago del depósito de fianza (figura \ref{fig:seq_pago_fianza}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_pago_fianza.png}
    \caption{Diagrama de secuencia de la aceptación de reserva y formalización del cobro de fianza}
    \label{fig:seq_pago_fianza}
\end{figure}

    El anfitrión revisa las solicitudes recibidas y acepta la propuesta desde la interfaz. El sistema verifica que el usuario sea el propietario y que la solicitud todavía esté pendiente. Cuando confirma el cambio, registra la aceptación y añade un aviso automático a la conversación del inquilino.

    El inquilino abona entonces la fianza desde su reserva. El sistema comprueba su identidad y confirma que el propietario haya aceptado previamente la solicitud. Tras verificar el cobro, registra el pago y convierte la reserva en confirmada. Las fechas se bloquean automáticamente para impedir que otro usuario reserve el mismo periodo.

    La adhesión a una vivienda compartida se gestiona mediante invitaciones temporales de acceso (figura \ref{fig:seq_adhesion_hogar}).

    El compañero de piso introduce el código alfanumérico generado previamente por el administrador del hogar. El servicio comprueba la vigencia temporal del código, verifica que no haya superado su límite de usos y comprueba que el solicitante no pertenezca ya a otra vivienda activa. Tras validar las precondiciones, el backend asocia la cuenta del usuario a la entidad del hogar, asigna el rol de compañero y emite eventos de dominio para actualizar el muro de actividad de los residentes.

    \subsection{Adhesión a un hogar mediante código de invitación}

La incorporación de un usuario a un grupo de convivencia se gestiona mediante códigos alfanuméricos compartidos, tal como muestra la figura \ref{fig:seq_adhesion_hogar}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_adhesion_hogar.png}
    \caption{Secuencia de generación de invitación y adhesión a un hogar}
    \label{fig:seq_adhesion_hogar}
\end{figure}

El flujo comprende dos interacciones separadas. En la primera, el administrador del piso entra en la configuración y solicita un código de invitación. El sistema verifica que el usuario tenga permisos de administración y genera una clave temporal. Cuando el código queda registrado, se muestra al administrador para que pueda compartirlo.

La segunda interacción sucede cuando otro usuario mete el código recibido en el formulario de unión. La petición va dirigida a POST /api/v1/homes/join. El backend localiza la vivienda con findByInvitationCodeAndDeletedAtIsNull. Si no hay coincidencias devuelve un 404. En caso de encontrarla, consulta en HomeMemberRepository si ese usuario ya figura con estado ACTIVE dentro del grupo, devolviendo un 400 si intenta duplicar la membresía. 

Al superar los filtros, se crea la fila en HomeMember con rol MEMBER, estado activo y un color de perfil asignado. Tras persistir al miembro, ApplicationEventPublisher emite un MemberJoinedEvent. El oyente ActivityLogListener atrapa este evento y guarda una fila en ActivityLogRepository para reflejar la entrada en el historial del grupo. El servidor finaliza devolviendo los datos actualizados del hogar al frontend para redirigir al nuevo miembro.

\subsection{Registro de gasto compartido y simplificación de balances}

El reparto de costes en la vivienda compartida y el cálculo de liquidaciones entre compañeros se ilustran en la figura \ref{fig:seq_registro_gasto}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_registro_gasto.png}
    \caption{Secuencia de registro de gasto compartido y simplificación de deudas}
    \label{fig:seq_registro_gasto}
\end{figure}

Al registrar un gasto, el usuario indica quién lo ha pagado y cómo se reparte entre los participantes. El sistema verifica que el usuario pertenezca al hogar y que las partes asignadas sumen exactamente el importe total. Si existe una diferencia por redondeo o aparece una cantidad negativa, rechaza el registro para evitar errores contables.

Con los datos comprobados, se crea la entidad HomeExpense, se añaden sus participantes vinculados y se guardan en bloque dentro de HomeExpenseRepository. En la misma transacción, el publicador de eventos de Spring lanza ExpenseCreatedEvent. El listener ActivityLogListener captura este evento e inserta de forma transparente una fila en ActivityLogRepository para que el movimiento figure en el historial del hogar. 

Para consultar el estado de cuentas, la aplicación reúne los gastos vigentes y calcula el saldo neto de cada compañero sumando lo pagado y restando lo debido. A continuación, simplifica las diferencias para proponer el menor número posible de pagos directos y saldar todas las deudas pendientes.

\subsection{Baja de un miembro del hogar y rebalanceo de tareas}

La desvinculación de un compañero del piso exige verificar que no existan deudas abiertas y reorganizar las obligaciones domésticas pendientes, como refleja la figura \ref{fig:seq_baja_miembro}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_baja_miembro.png}
    \caption{Secuencia de baja de un miembro y rebalanceo de tareas huérfanas}
    \label{fig:seq_baja_miembro}
\end{figure}

El proceso empieza cuando el usuario solicita abandonar el piso desde la configuración. El sistema revisa sus gastos y transferencias pendientes. Si todavía debe dinero o tiene pagos por cobrar, impide la salida hasta que las cuentas queden equilibradas.

Si el balance neto es exactamente cero, el servicio actualiza el estado del miembro a LEFT y persiste el cambio en la base de datos. A continuación se emite el evento de dominio MemberLeftEvent mediante ApplicationEventPublisher. Este evento lo reciben dos componentes en paralelo: ChoreMemberLeftListener, que busca en ChoreRepository las tareas sin completar asignadas al usuario saliente para ponerlas en estado no asignado o redistribuirlas entre el resto de integrantes, y ActivityLogListener, que añade el apunte de salida en ActivityLogRepository para que conste en el historial de actividad de la casa. El endpoint responde con un código 204 y el navegador saca al usuario del panel del piso.

\subsection{Planificación periódica de tareas domésticas y rescate gamificado}

El módulo de tareas gestiona las responsabilidades del hogar mediante calendarios rotativos y un sistema de rescates que premia la proactividad de los compañeros (figura \ref{fig:seq_planificacion_tareas}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_planificacion_tareas.png}
    \caption{Secuencia de creación de serie de tareas y resolución de rescate con puntos}
    \label{fig:seq_planificacion_tareas}
\end{figure}

El flujo se divide en dos fases. En la primera, el usuario define una labor periódica indicando el intervalo de repetición y los participantes. El sistema guarda la regla y distribuye los turnos de forma equitativa. Las tareas individuales aparecen automáticamente en el calendario compartido.

La segunda fase modela el rescate gamificado. Si una tarea supera su fecha límite sin completarse, pasa a estado vencida. Cualquier compañero distinto del responsable puede realizarla y solicitar el rescate. El sistema comprueba que la tarea esté vencida y que el solicitante no fuese el responsable original antes de conceder los puntos.

Al pasar las comprobaciones, entra en juego ChorePointCalculator. Este componente asigna puntos de recompensa al rescatador e impone una penalización en la clasificación al responsable que descuidó la obligación. La entidad se actualiza marcando el estado COMPLETED y guardando la referencia de quién hizo el rescate. Tras persistir la tarea, se dispara ChoreRescuedEvent para que ActivityLogListener inserte el movimiento en el historial del hogar, actualizando las puntuaciones de la convivencia en la interfaz de React.

\subsection{Asistente conversacional mediante orquestación MCP y tickets de sesión}

La integración del asistente inteligente utiliza el protocolo MCP (\emph{Model Context Protocol}) para permitir que el modelo consulte datos reales del piso sin comprometer las credenciales del usuario (figura \ref{fig:seq_asistente_mcp}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_asistente_mcp.png}
    \caption{Secuencia de consulta al asistente de IA con ejecución de herramientas MCP}
    \label{fig:seq_asistente_mcp}
\end{figure}

El proceso requiere dos llamadas sucesivas desde la interfaz. En primer lugar, al abrir el widget de soporte en React, la aplicación lanza un POST a /api/v1/ai/ticket. McpTicketService genera un token de un solo uso con tiempo de expiración reducido vinculado al ID del usuario autenticado. Este ticket evita reenviar el token JWT principal a los subsistemas del modelo y delimita el alcance de las operaciones que la IA podrá consultar.

Una vez obtenido el ticket, el usuario envía su pregunta a POST /api/v1/ai/chat adjuntando el ticket y el histórico reciente de mensajes. SpringAiOrchestratorServiceImpl valida primero la vigencia del ticket con McpTicketService. Si el token ha caducado, la petición se corta de inmediato con un 401 para obligar a regenerar la sesión. 

Al superar la validación, el orquestador carga el contexto inicial desde AiPromptProvider y contacta con el servidor MCP local por medio de McpClientFactory. Este servidor expone las funciones disponibles de la aplicación, como la lectura de tareas asignadas o el balance de gastos. El orquestador envía la consulta junto con el catálogo de funciones al proveedor de IA mediante las librerías de Spring AI. Si el modelo necesita datos concretos para responder, solicita una llamada de herramienta (\emph{tool call}). El backend ejecuta la función solicitada sobre el servidor MCP, devuelve el resultado al modelo y este genera la redacción final que el controlador entrega al cliente web en un objeto AiChatResponse.

\subsection{Moderación de denuncias, auditoría de conversaciones y suspensión de cuentas}

El panel de administración permite investigar incidencias reportadas por los usuarios, revisar el historial de mensajes de forma forense y aplicar sanciones sobre cuentas infractoras (figura \ref{fig:seq_moderacion_denuncias}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_moderacion_denuncias.png}
    \caption{Secuencia de resolución de denuncias, inspección de chat y baneo de usuario}
    \label{fig:seq_moderacion_denuncias}
\end{figure}

El flujo arranca cuando un administrador entra en la sección de moderación del panel de control. Puede consultar los detalles de cada denuncia y revisar el historial de las conversaciones relacionadas. Al hacerlo, accede temporalmente a las pruebas necesarias para comprobar si existieron conductas de acoso o estafa.

Comprobada la infracción, el administrador tramita la suspensión desde la vista de detalle. Indica el motivo y la duración de la sanción. A partir de ese momento, el usuario no puede utilizar su cuenta hasta que finalice el bloqueo.

Para terminar el trámite, el moderador cierra el expediente e incluye una nota de resolución. El sistema registra el resultado y comunica al usuario que presentó la denuncia qué decisión se ha adoptado, sin revelar datos privados del infractor.
