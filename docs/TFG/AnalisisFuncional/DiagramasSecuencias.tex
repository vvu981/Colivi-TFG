\section{Diagramas de secuencia del sistema}
\label{sec:diagramas_secuencia}

    Los diagramas de secuencia UML 2.5 detallan la dimensión temporal y el intercambio cronológico de mensajes entre componentes: el cliente en React, los controladores REST, los servicios de aplicación en Spring Boot, los publicadores de eventos de dominio, la base de datos PostgreSQL y los servicios externos conectados.

    La plataforma implementa ochenta y seis casos de uso, pero la mayoría realiza operaciones estándar de lectura o actualización. Se seleccionaron diez escenarios con lógica distribuida, salvaguardas de concurrencia o sincronización asíncrona:

\begin{enumerate}
\item Recuperación segura de contraseña con doble fase y mitigación de enumeración.
\item Alta de inmueble base con geocodificación cartográfica y compensación transaccional.
\item Solicitud de reserva con validación temporal de calendario y notificación multicanal.
\item Transición de estados y formalización del cobro de fianza en reserva aceptada.
\item Adhesión a un espacio de convivencia mediante código efímero y asignación de membresía.
\item Registro de gasto compartido con cálculo de matriz contable y simplificación de balances.
\item Baja o expulsión de un miembro con validación de saldo cero y rebalanceo de tareas.
\item Planificación periódica de tareas domésticas y resolución de rescate gamificado.
\item Interacción con el asistente inteligente mediante ticket efímero y protocolo MCP.
\item Tramitación y resolución de denuncias con auditoría de chat y suspensión cautelar.
\end{enumerate}

    La recuperación de credenciales opera en dos fases desacopladas (figura \ref{fig:seq_recuperacion_contrasena}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_recuperacion_contrasena.png}
    \caption{Diagrama de secuencia del proceso de recuperación segura de contraseña}
    \label{fig:seq_recuperacion_contrasena}
\end{figure}

    El usuario introduce su correo electrónico en el formulario web. El sistema aplica una política de defensa contra ataques de enumeración de cuentas (\emph{Anti User-Enumeration}): si la dirección no existe en la base de datos o la cuenta está suspendida, el servicio genera una traza interna y retorna un código HTTP 200 con cuerpo vacío. La interfaz muestra un mensaje estándar de confirmación. Ningún atacante puede inferir qué cuentas están dadas de alta. Si la cuenta existe, se genera un identificador UUID temporal con 24 horas de validez y se persiste en base de datos. \texttt{ApplicationEventPublisher} dispara de inmediato la notificación en segundo plano para que el servicio de correo despache el mensaje sin bloquear la respuesta HTTP al cliente.

    El restablecimiento concluye cuando el usuario abre el enlace con el token temporal e introduce la nueva contraseña. El backend comprueba la existencia del token y verifica que no haya vencido la marca de tiempo. Si la validación es correcta, la clave se procesa con el algoritmo de dispersión (\emph{hashing}) con sal criptográfica, se invalida el token temporal y se persiste la entidad, retornando un código 204 que redirige al usuario hacia el formulario de inicio de sesión.

    El alta de propiedades físicas combina geocodificación cartográfica con almacenamiento multimedia (figura \ref{fig:seq_alta_inmueble}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_alta_inmueble.png}
    \caption{Diagrama de secuencia del alta de inmueble con geocodificación y compensación transaccional}
    \label{fig:seq_alta_inmueble}
\end{figure}

    El proceso se divide en dos fases. El anfitrión introduce la dirección postal en el formulario del cliente web. La aplicación consulta el servicio de cartografía Nominatim (OpenStreetMap) para transformar el texto en coordenadas espaciales (latitud y longitud), posicionando el marcador en el mapa de Leaflet. Tras validar los campos estructurales (metros cuadrados, dormitorios y servicios), la petición viaja a \texttt{POST /api/v1/accommodations}. El controlador \texttt{AccommodationController} traslada la carga a \texttt{AccommodationServiceImpl}, donde la entidad se enlaza con el anfitrión mediante una referencia perezosa de JPA (\texttt{userRepository.getReferenceById}) y se persiste en PostgreSQL, retornando el identificador del alojamiento.

    La segunda fase gestiona la subida de fotos sobre \texttt{POST /api/v1/accommodations/\{id\}/images} con salvaguarda contra fugas de almacenamiento (\emph{Storage Leak Prevention}). Subir el archivo binario a Cloudinary mediante \texttt{IImageStorageService} y persistir la URL en la base de datos relacional no admite una transacción distribuida 2PC nativa. Por ello, la capa de servicio se apoya en \texttt{TransactionSynchronizationManager}. El servicio sube la imagen, recibe la URL segura y solicita registrarla en la base de datos. Si la base de datos aborta la transacción por violación de restricciones o caída de red, el manejador detecta el \emph{rollback} en la fase posterior (\texttt{afterCompletion}) y elimina inmediatamente el archivo huérfano de los servidores de Cloudinary. El almacenamiento en la nube se mantiene sincronizado con las tablas relacionales.

    La solicitud de reserva gestiona restricciones de calendario y comunicación asíncrona entre las partes (figura \ref{fig:seq_solicitud_reserva}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_solicitud_reserva.png}
    \caption{Diagrama de secuencia de la solicitud de reserva con validación temporal y notificación multicanal}
    \label{fig:seq_solicitud_reserva}
\end{figure}

    El inquilino selecciona las fechas en el calendario interactivo y envía la petición mediante \texttt{POST /api/v1/booking-requests}. \texttt{BookingRequestController} recupera la identidad del solicitante desde el token JWT y traslada el objeto \texttt{BookingRequestDto} a \texttt{BookingRequestServiceImpl}. Antes de modificar datos, \texttt{BookingRequestValidator} ejecuta validaciones en cadena: comprueba que el usuario esté activo sin sanciones, que el anuncio permanezca publicado, que el solicitante no sea el dueño del inmueble, que no existan solicitudes duplicadas en trámite y que las fechas no colisionen con reservas confirmadas.

    Tras validar todas las reglas, el servicio instancia la entidad \texttt{BookingRequest} en estado \texttt{PENDING} y la persiste atómicamente en \texttt{BookingRequestRepository}. La transacción publica el evento de dominio \texttt{BookingRequestCreatedEvent} mediante \texttt{ApplicationEventPublisher}. Dos componentes escuchan este evento de forma desacoplada: \texttt{BookingNotificationListener} invoca a \texttt{EmailService} para redactar y enviar un correo transaccional al propietario, mientras \texttt{BookingStatusChangedListener} utiliza \texttt{MessageService} para registrar una notificación automática de sistema dentro de la conversación vinculada al anuncio. El controlador devuelve un código HTTP 201 con el DTO \texttt{BookingRequestResponseDto} confirmando el registro.

    La consolidación de la reserva se produce mediante la aprobación del anfitrión y el pago del depósito de fianza (figura \ref{fig:seq_pago_fianza}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_pago_fianza.png}
    \caption{Diagrama de secuencia de la aceptación de reserva y formalización del cobro de fianza}
    \label{fig:seq_pago_fianza}
\end{figure}

    El anfitrión revisa las solicitudes recibidas y acepta la propuesta llamando a \texttt{PATCH /api/v1/booking-requests/\{id\}/status} con estado \texttt{ACCEPTED}. \texttt{BookingRequestServiceImpl} comprueba que el usuario autenticado sea el titular del inmueble y que la solicitud se encuentre en estado \texttt{PENDING}. Al persistir el cambio, se dispara el evento \texttt{BookingStatusChangedEvent}. El componente \texttt{BookingStatusChangedListener} intercepta el evento e inserta un mensaje de aviso en el chat del inquilino.

    El inquilino abona entonces la fianza mediante \texttt{POST /api/v1/booking-requests/\{id\}/confirm-payment} enviando el DTO \texttt{PaymentConfirmationDto}. El servicio comprueba que quien paga sea el inquilino de la solicitud y que el estado sea \texttt{ACCEPTED}. \texttt{PaymentService} procesa y concilia la transacción económica. Al verificarse el cobro, la entidad \texttt{BookingRequest} guarda los metadatos del pago, conmuta su estado a \texttt{CONFIRMED} y se almacena en base de datos. Se publica el evento \texttt{BookingConfirmedEvent}, permitiendo que \texttt{BookingConfirmedEventListener} bloquee definitivamente el rango de fechas en el calendario del piso frente a peticiones concurrentes.

    La adhesión a una vivienda compartida se gestiona mediante invitaciones temporales de acceso (figura \ref{fig:seq_adhesion_hogar}).

    El compañero de piso introduce el código alfanumérico generado previamente por el administrador del hogar. El servicio comprueba la vigencia temporal del código, verifica que no haya superado su límite de usos y comprueba que el solicitante no pertenezca ya a otra vivienda activa. Tras validar las precondiciones, el backend asocia la cuenta del usuario a la entidad del hogar, asigna el rol de compañero y emite eventos de dominio para actualizar el muro de actividad de los residentes.

    \subsection{Adhesión a un hogar mediante código de invitación}

La incorporación de un usuario a un grupo de convivencia se gestiona mediante códigos alfanuméricos compartidos, tal como muestra la figura \ref{fig:seq_adhesion_hogar}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_adhesion_hogar.png}
    \caption{Secuencia de generación de invitación y adhesión a un hogar}
    \label{fig:seq_adhesion_hogar}
\end{figure}

El flujo comprende dos interacciones separadas. En la primera, el administrador del piso entra al apartado de configuración y solicita un código. El frontend lanza una llamada a \texttt{POST /api/v1/homes/\{id\}/invitation-code}. Dentro de \texttt{HomeServiceImpl}, se rescata el hogar de PostgreSQL y se revisa si el usuario logueado ostenta el rol de administrador. Si no lo es, salta una \texttt{UnauthorizedActionException} que corta la petición con un error 403. Si el permiso es válido, el servicio delega en \texttt{InvitationCodeGenerator} para crear una clave aleatoria, actualiza la propiedad en la entidad y guarda los cambios en \texttt{HomeRepository}, entregando el código a la interfaz.

La segunda interacción sucede cuando otro usuario mete el código recibido en el formulario de unión. La petición va dirigida a \texttt{POST /api/v1/homes/join}. El backend localiza la vivienda con \texttt{findByInvitationCodeAndDeletedAtIsNull}. Si no hay coincidencias devuelve un 404. En caso de encontrarla, consulta en \texttt{HomeMemberRepository} si ese usuario ya figura con estado \texttt{ACTIVE} dentro del grupo, devolviendo un 400 si intenta duplicar la membresía. 

Al superar los filtros, se crea la fila en \texttt{HomeMember} con rol \texttt{MEMBER}, estado activo y un color de perfil asignado. Tras persistir al miembro, \texttt{ApplicationEventPublisher} emite un \texttt{MemberJoinedEvent}. El oyente \texttt{ActivityLogListener} atrapa este evento y guarda una fila en \texttt{ActivityLogRepository} para reflejar la entrada en el historial del grupo. El servidor finaliza devolviendo los datos actualizados del hogar al frontend para redirigir al nuevo miembro.

\subsection{Registro de gasto compartido y simplificación de balances}

El reparto de costes en la vivienda compartida y el cálculo de liquidaciones entre compañeros se ilustran en la figura \ref{fig:seq_registro_gasto}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_registro_gasto.png}
    \caption{Secuencia de registro de gasto compartido y simplificación de deudas}
    \label{fig:seq_registro_gasto}
\end{figure}

Al introducir un ticket en la aplicación, el usuario especifica quién ha pagado el importe y cómo se divide entre los participantes. El cliente React envía un POST a \texttt{/api/v1/homes/\{homeId\}/expenses} enviando el DTO \texttt{CreateExpenseRequest}. En \texttt{HomeExpenseServiceImpl}, se comprueba que el usuario autenticado forme parte del piso con estado activo en \texttt{HomeMemberRepository}. Si no pertenece al hogar, la petición se rechaza con un 403. El servicio también verifica que los importes asignados a cada compañero en la lista de participantes sumen exactamente el total del gasto. Si hay desfases por redondeo o importes negativos, salta una \texttt{BusinessRuleValidationException} con código 400.

Con los datos comprobados, se crea la entidad \texttt{HomeExpense}, se añaden sus participantes vinculados y se guardan en bloque dentro de \texttt{HomeExpenseRepository}. En la misma transacción, el publicador de eventos de Spring lanza \texttt{ExpenseCreatedEvent}. El listener \texttt{ActivityLogListener} captura este evento e inserta de forma transparente una fila en \texttt{ActivityLogRepository} para que el movimiento figure en el historial del hogar. 

Para consultar el estado de cuentas, la aplicación web solicita los balances a \texttt{GET /api/v1/homes/\{homeId\}/expenses/balances}. La capa de servicio extrae los gastos vigentes, calcula el saldo neto de cada compañero sumando lo pagado y restando lo debido, y le pasa la matriz de saldos al algoritmo de \texttt{DebtSimplifierService}. Este componente procesa las diferencias y genera una lista de transferencias mínimas (\texttt{DebtTransfer}) para liquidar las deudas pendientes con el menor número posible de pagos directos.

\subsection{Baja de un miembro del hogar y rebalanceo de tareas}

La desvinculación de un compañero del piso exige verificar que no existan deudas abiertas y reorganizar las obligaciones domésticas pendientes, como refleja la figura \ref{fig:seq_baja_miembro}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_baja_miembro.png}
    \caption{Secuencia de baja de un miembro y rebalanceo de tareas huérfanas}
    \label{fig:seq_baja_miembro}
\end{figure}

El proceso empieza cuando el usuario solicita abandonar el piso desde la vista de ajustes mediante una petición POST a \texttt{/api/v1/homes/\{homeId\}/leave}. Dentro de \texttt{HomeServiceImpl}, se rescata la membresía activa en \texttt{HomeMemberRepository}. Acto seguido interviene \texttt{HomeBalanceValidator} para examinar los gastos y transferencias registradas de la vivienda. Si el usuario debe dinero o tiene pagos pendientes de cobro con sus compañeros, el validador corta la transacción lanzando una \texttt{BusinessRuleValidationException} que se traduce en un código 400. De este modo se impide que ningún integrante abandone el grupo dejando saldos descompensados en la contabilidad.

Si el balance neto es exactamente cero, el servicio actualiza el estado del miembro a \texttt{LEFT} y persiste el cambio en la base de datos. A continuación se emite el evento de dominio \texttt{MemberLeftEvent} mediante \texttt{ApplicationEventPublisher}. Este evento lo reciben dos componentes en paralelo: \texttt{ChoreMemberLeftListener}, que busca en \texttt{ChoreRepository} las tareas sin completar asignadas al usuario saliente para ponerlas en estado no asignado o redistribuirlas entre el resto de integrantes, y \texttt{ActivityLogListener}, que añade el apunte de salida en \texttt{ActivityLogRepository} para que conste en el historial de actividad de la casa. El endpoint responde con un código 204 y el navegador saca al usuario del panel del piso.

\subsection{Planificación periódica de tareas domésticas y rescate gamificado}

El módulo de tareas gestiona las responsabilidades del hogar mediante calendarios rotativos y un sistema de rescates que premia la proactividad de los compañeros (figura \ref{fig:seq_planificacion_tareas}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_planificacion_tareas.png}
    \caption{Secuencia de creación de serie de tareas y resolución de rescate con puntos}
    \label{fig:seq_planificacion_tareas}
\end{figure}

El flujo se divide en dos fases. En la primera, el usuario define una labor periódica indicando el intervalo de repetición y los miembros participantes en la vista web. El formulario manda un POST a \texttt{/api/v1/homes/\{homeId\}/chores} con el DTO \texttt{CreateChoreRequest}. En \texttt{ChoreServiceImpl}, se guarda la regla recurrente en \texttt{ChoreSeriesRepository} y se invoca a \texttt{ChoreRotationService}. Este servicio calcula los turnos equitativos entre los compañeros mediante algoritmos de rotación y genera las tareas individuales que se insertan en \texttt{ChoreRepository}, quedando visibles en el calendario compartido de la vivienda.

La segunda fase modela el rescate gamificado. Si una tarea supera su fecha límite sin completarse, su estado pasa a \texttt{OVERDUE}. Cualquier compañero distinto del asignado puede completarla haciendo una petición a \texttt{POST /api/v1/homes/\{homeId\}/chores/\{choreId\}/rescue}. El servicio comprueba dos condiciones antes de procesar el rescate: que la tarea esté realmente vencida y que el usuario que intenta rescatarla no sea el responsable original. Si se incumplen, se aborta con un código 400.

Al pasar las comprobaciones, entra en juego \texttt{ChorePointCalculator}. Este componente asigna puntos de recompensa al rescatador e impone una penalización en la clasificación al responsable que descuidó la obligación. La entidad se actualiza marcando el estado \texttt{COMPLETED} y guardando la referencia de quién hizo el rescate. Tras persistir la tarea, se dispara \texttt{ChoreRescuedEvent} para que \texttt{ActivityLogListener} inserte el movimiento en el historial del hogar, actualizando las puntuaciones de la convivencia en la interfaz de React.

\subsection{Asistente conversacional mediante orquestación MCP y tickets de sesión}

La integración del asistente inteligente utiliza el protocolo MCP (\emph{Model Context Protocol}) para permitir que el modelo consulte datos reales del piso sin comprometer las credenciales del usuario (figura \ref{fig:seq_asistente_mcp}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_asistente_mcp.png}
    \caption{Secuencia de consulta al asistente de IA con ejecución de herramientas MCP}
    \label{fig:seq_asistente_mcp}
\end{figure}

El proceso requiere dos llamadas sucesivas desde la interfaz. En primer lugar, al abrir el widget de soporte en React, la aplicación lanza un POST a \texttt{/api/v1/ai/ticket}. \texttt{McpTicketService} genera un token de un solo uso con tiempo de expiración reducido vinculado al ID del usuario autenticado. Este ticket evita reenviar el token JWT principal a los subsistemas del modelo y delimita el alcance de las operaciones que la IA podrá consultar.

Una vez obtenido el ticket, el usuario envía su pregunta a \texttt{POST /api/v1/ai/chat} adjuntando el ticket y el histórico reciente de mensajes. \texttt{SpringAiOrchestratorServiceImpl} valida primero la vigencia del ticket con \texttt{McpTicketService}. Si el token ha caducado, la petición se corta de inmediato con un 401 para obligar a regenerar la sesión. 

Al superar la validación, el orquestador carga el contexto inicial desde \texttt{AiPromptProvider} y contacta con el servidor MCP local por medio de \texttt{McpClientFactory}. Este servidor expone las funciones disponibles de la aplicación, como la lectura de tareas asignadas o el balance de gastos. El orquestador envía la consulta junto con el catálogo de funciones al proveedor de IA mediante las librerías de Spring AI. Si el modelo necesita datos concretos para responder, solicita una llamada de herramienta (\emph{tool call}). El backend ejecuta la función solicitada sobre el servidor MCP, devuelve el resultado al modelo y este genera la redacción final que el controlador entrega al cliente web en un objeto \texttt{AiChatResponse}.

\subsection{Moderación de denuncias, auditoría de conversaciones y suspensión de cuentas}

El panel de administración permite investigar incidencias reportadas por los usuarios, revisar el historial de mensajes de forma forense y aplicar sanciones sobre cuentas infractoras (figura \ref{fig:seq_moderacion_denuncias}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{AnalisisFuncional/img/seq_moderacion_denuncias.png}
    \caption{Secuencia de resolución de denuncias, inspección de chat y baneo de usuario}
    \label{fig:seq_moderacion_denuncias}
\end{figure}

El flujo arranca cuando un administrador entra en la sección de moderación del panel de control. La interfaz React llama a \texttt{GET /api/v1/admin/reports/\{id\}} para recuperar los detalles del expediente desde \texttt{ReportRepository}. Si la denuncia implica comunicaciones indebidas, el administrador solicita las pruebas vinculadas mediante una petición a \texttt{GET /api/v1/admin/conversations/\{convId\}/dossier}. En este punto, \texttt{AdminConversationServiceImpl} rescata la conversación completa con sus mensajes asociados. Este endpoint salta los filtros de privacidad habituales de los participantes para que el moderador pueda leer el historial íntegro y verificar si hubo conductas de acoso o estafa.

Comprobada la infracción, el administrador tramita la suspensión desde la vista de detalle. El cliente manda un POST a \texttt{/api/v1/admin/users/\{userId\}/ban} pasando el motivo y el plazo de la sanción en el cuerpo \texttt{BanRequest}. En \texttt{UserServiceImpl}, se carga el usuario denunciado, se activan los indicadores de bloqueo (\texttt{isBanned = true}) junto con la causa de la sanción y se persiste el estado en \texttt{UserRepository}. Al guardar el cambio, cualquier petición futura que intente realizar ese usuario con su token JWT será interceptada con un error 403 por el filtro de seguridad de la aplicación.

Para terminar el trámite, el moderador cierra el expediente haciendo un PATCH a \texttt{/api/v1/admin/reports/\{id\}/status} con estado \texttt{RESOLVED} y una nota de resolución. \texttt{AdminReportServiceImpl} guarda la actualización en PostgreSQL y lanza \texttt{ReportResolvedEvent}. El componente \texttt{ReportNotificationListener} recibe el aviso y delega en \texttt{EmailService} para mandar un correo al usuario que puso la queja, explicándole la resolución adoptada sin revelar datos protegidos del infractor.
